= Architecture Decisions
:page-layout: default

Capture the architectural choices that deserve durable context.

== Decision Log

=== ADR-0001: Native `{{ }}` compiler replaces the EEx pipeline

Accepted (2026-05-21).

*Context.* Stem began as Elixir's EEx engine with a preprocessor that rewrote `{{ }}` into EEx text.
That layer leaked EEx semantics, escaping markers, and error messages, and constrained the language to what EEx allowed.

*Decision.* Build a native pipeline (`Stem.Tokenizer`, `Stem.Parser`, `Stem.AST`, `Stem.Compiler`, `Stem.Expression`) that emits Elixir AST directly, and remove the EEx surface entirely.

*Consequences.* Stem owns its grammar, error reporting, and code generation, at the cost of maintaining a real compiler.
The `<%= %>` tag family, the engine behaviour and custom engines, the public EEx tokenizer, and the `:engine`/`:trim`/`:parser_options` options were removed without a compatibility layer.

See `papers/00004-native-compiler-minutes.adoc` for the full record.

=== ADR-0002: Runtime compile/eval APIs alongside compile-time macros

Accepted (2026-03-05, revised 2026-05-21).

*Context.* Some consumers need dynamic template evaluation at runtime, similar to EEx workflows.

*Decision.* Stem keeps compile-time macros and also provides runtime `compile_string/2`, `compile_file/2`, `eval_string/3`, and `eval_file/3` APIs.
Output rendering remains unescaped by default and transformations are explicit via helpers.

*Consequences.* Runtime evaluation is supported directly, so callers must enforce trust boundaries around template input.
Escaping and sanitization are explicit responsibilities of helper functions and calling code.

=== ADR-0003: Explicit Data Boundaries and CLI Contract

Accepted (2026-05-21).

*Context.* The CLI previously allowed flexible inline JSON data directly in the positional arguments (`stem template.stem '{"key": "value"}'`), which mixed string evaluation with file paths.

*Decision.* Remove inline JSON from the positional CLI contract. Establish a Mustache-style contract: one argument (`stem template.stem`) means the template gets bound to JSON read from standard input. Two arguments (`stem data.json template.stem`) mean file-backed data first, then the template.

*Consequences.* The CLI behavior is strictly file-based or pipe-based, avoiding ambiguity and reinforcing Stem's philosophy of explicit data separation and strict input boundaries.

=== ADR-0004: Structured-Only Expressions (No Arbitrary-Elixir Escape Hatch)

Accepted (2026-05-25). Supersedes the original `allow_elixir_expressions` boolean-flag approach (Accepted 2026-05-22).

*Context.* Runtime template evaluation introduces Server-Side Template Injection (SSTI) risk. The earlier design gated arbitrary Elixir behind an `allow_elixir_expressions` flag (default off) plus a `mix stem.audit` CI gate. That escape hatch proved non-portable (it relies on the BEAM compiler; the native/Rust engine has no equivalent), and an opt-in to arbitrary code execution is a footgun even when guarded.

*Decision.* Remove the escape hatch entirely. Templates accept only structured Stem syntax — assigns, dotted paths, literals, and transformer calls. An unrecognised expression raises `Stem.SyntaxError` at parse time. The `allow_elixir_expressions` flag, the `{:elixir, …}` AST node, and the `mix stem.audit` task are removed.

*Consequences.* The language is identical across backends (BEAM and native) and SSTI via arbitrary expressions is impossible by construction — there is no flag to misconfigure and no CI gate to maintain. The remaining trust boundary is the *template source* itself, which is why runtime evaluation stays under `Stem.Unsafe`. Logic that previously reached for arbitrary expressions belongs in a registered helper or a backend service.
