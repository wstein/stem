= Cross-Cutting Concepts
:page-layout: default

Use this chapter for concepts that apply across multiple building blocks.

== Security and HTML Escaping

Stem is **secure by default**: `{{ expression }}` output is **automatically HTML escaped** to prevent XSS attacks.
Use `{{{ expression }}}` for raw output only when you know the content is safe.

Escape modes can be configured globally via `.stem.config.json` or per-call:

* **HTML escaping (default)** — Prevents XSS attacks
* **Raw output (`:none`)** — Use with caution only for trusted content
* **Other modes** — `:xml`, `:json`, `:url`, or custom escape functions

Keeping the rendering model explicit makes security-sensitive formatting decisions visible at the call site.
Callers must treat all dynamically selected templates and user-provided context as untrusted.

== Execution Modes: Restricted vs. Unrestricted

Stem enforces control over arbitrary Elixir expression execution via the `allow_elixir_expressions` flag:

* **`allow_elixir_expressions: false` (default, recommended)** — Restricts templates to structured Stem expressions, literals, helpers, and variable paths. Forbids arbitrary Elixir code. Protects against Server-Side Template Injection (SSTI). This is the required mode for all production templates.

* **`allow_elixir_expressions: true`** — Allows arbitrary Elixir expressions. Maximum flexibility but should only be used for development and local experiments when the template source is entirely trusted and controlled by your team. Passing `allow_elixir_expressions: true` serves as a visible code-review flag.

Runtime evaluation APIs (`Stem.Unsafe.eval_string/3` and `Stem.Unsafe.eval_file/3`) default to `allow_elixir_expressions: false`, requiring explicit opt-in to use `allow_elixir_expressions: true`.
If you feel forced to enable arbitrary expressions in production, this indicates an architectural flaw: business logic is leaking into the presentation layer and should be refactored into helpers or backend services.

== Transformer Capability Groups

Beyond restricting arbitrary Elixir code, Stem also enforces capability management for transformer functions.
A template has access only to the transformers it explicitly needs, reducing Server-Side Template Injection (SSTI) attack surface through **principle of least privilege**.

The secure minimum (`Stem.Transformers.Minimum`) is always available as built-ins and contains only essential transformers for XSS protection and output formatting.
Complex data operations (filtering, sorting, grouping, transformation) are organized into optional capability groups:

* `Stem.Transformers.Strings` — Text manipulation
* `Stem.Transformers.Collections` — Data transformation and filtering
* `Stem.Transformers.Predicates` — Boolean predicates for conditionals

Templates declare which groups they need via the `transformers:` map — call `.all()` on each group and merge:

[source,elixir]
----
Stem.Unsafe.eval_string(template, assigns: data,
  transformers: Stem.Transformers.Collections.all())
----

Or via `.stem.config.json` defaults:

[source,json]
----
{
  "transformers": "Stem.Transformers.Collections,Stem.Transformers.Strings"
}
----

*Rationale:* In an SSTI attack, an attacker can chain powerful operations (map, filter, group_by) to extract internal state or manipulate data.
By restricting access to only approved groups, Stem minimizes the "gadget chains" available for exploitation.
The requirement to explicitly declare which operations are needed makes dangerous choices visible during code review.

=== Collections capability audit signal

Because `Stem.Transformers.Collections` is the most powerful group, every call to `Collections.all/0` emits an
audit signal.
When the `:telemetry` application is present, it dispatches a `[:stem, :capability_group, :loaded]` event:

[source,elixir]
----
:telemetry.attach(
  "stem-collections-audit",
  [:stem, :capability_group, :loaded],
  fn _event, _measurements, %{group: group}, _config ->
    Logger.warning("Stem capability group loaded: #{inspect(group)}")
  end,
  nil
)
----

When `:telemetry` is not in the application tree, a `Logger.warning` is emitted instead so nothing crashes.

== Explicit Data Boundaries

Stem preserves an explicit boundary between data and templates at all levels.
In the CLI, the command contract differentiates between file-backed JSON (`mix stem data.json template.stem`) and stdin-piped JSON (`echo '{}' | mix stem template.stem`), avoiding implicit ambiguity parsing strings versus files.

== Whitespace Control

Stem provides declarative, tag-level whitespace control using the `~` character.
Whitespace logic allows adjusting spacing around rendered content without littering source files with unreadable formatting:

* `{{~ ... ~}}`: Trims literal whitespace symmetrically before and after the tag.
* `{{~ ... }}` and `{{ ... ~}}`: Trims whitespace precisely on the given side (one-sided trim).

`Stem.Formatter` normalises the visual noise produced by these markers — spaces between the braces
and the tilde are removed during formatting so source files stay readable without any semantic change.

== Template Formatter Plugin

`Stem.Formatter` implements the `Mix.Tasks.Format` behaviour, making it a standard Elixir formatter
plugin.
Declaring it in `.formatter.exs` causes `mix format` to process `.stem` files alongside Elixir sources
in one command:

[source,elixir]
----
# .formatter.exs
[
  plugins: [Stem.Formatter],
  inputs: [
    "{mix,.formatter}.exs",
    "{config,lib,test}/**/*.{ex,exs}",
    "templates/**/*.stem"
  ]
]
----

This integration enables:

* Automatic formatting on `mix format` in CI and editor save hooks.
* `mix format --check-formatted` validation that covers both Elixir and Stem files.
* Zero-friction adoption — no separate `mix stem.format` step required.

The `mix stem.format` standalone task still exists for direct invocations and file-glob patterns.

== Assign Contracts

Templates can declare a typed assign contract using the `contract:` option, modelled on ST4 Group Interfaces.
Contracts are evaluated at two points:

. *Compile time*: `Stem.Contract.validate_types!/1` rejects unknown type annotations before code is generated.
. *Render time*: `Stem.Contract.validate!/2` raises `ArgumentError` if required assigns are missing or typed assigns have the wrong type.

[source,elixir]
----
Stem.function_from_string(:def, :render, "{{title}} ({{count}})", [:assigns],
  contract: [
    required: [title: :string, count: :integer],
    optional: [active: :boolean]
  ])
----

A shared contract module can be referenced by atom, providing a single interface definition for many templates:

[source,elixir]
----
deftemplate :article, "{{title}}", [:assigns],
  contract: MyApp.Contracts.ArticleView  # must export contract/0
----

Supported types: `:string`, `:integer`, `:float`, `:number`, `:boolean`, `:atom`, `:list`, `:map`, `:any`.

== CI Security Gate

`mix stem.audit` is a static analysis gate that scans config files for `allow_elixir_expressions: true`
and fails the build (exit code 1) on any violation.
Add it to CI pipelines to prevent configuration drift from accidentally re-enabling SSTI-vulnerable
expression evaluation in production:

[source,yaml]
----
# .github/workflows/ci.yml
- run: mix stem.audit
----

The task scans `config/prod.exs` and `config/runtime.exs` by default.
Use `--paths` to scan additional files.
Each violation is reported with file path, line number, and the offending line.
