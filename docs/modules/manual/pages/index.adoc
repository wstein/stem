== Command Line Interface (CLI)

Stem ships with an explicit, file-centric CLI that allows you to easily format and execute templates from your shell.

=== Formatting Templates

To format your `.stem` template files, use the `mix stem.format` task directly:

[source,sh]
----
mix stem.format "lib/**/*.stem"
mix stem.format --check-formatted path/to/template.stem
----

Or declare `Stem.Formatter` as a formatter plugin in `.formatter.exs` so that `mix format` handles `.stem` files automatically alongside Elixir sources:

[source,elixir]
----
# .formatter.exs
[
  plugins: [Stem.Formatter],
  inputs: [
    "{mix,.formatter}.exs",
    "{config,lib,test}/**/*.{ex,exs}",
    "templates/**/*.stem"
  ]
]
----

With the plugin declared, `mix format` and `mix format --check-formatted` cover both Elixir and Stem files in a single command.

=== Rendering Templates

The CLI supports strict file or standard input models for binding data, modeled after standard Mustache CLI tooling conventions.

*File-backed Data and Template:*
When providing two positional arguments, the first specifies a JSON data file and the second points to the `.stem` template file:

[source,sh]
----
mix stem data.json template.stem
----

*Standard Input Interpolation:*
When providing a single positional argument, the CLI reads the JSON object from the pipeline standard input and applies it to the template:

[source,sh]
----
echo '{"name":"Nina"}' | mix stem template.stem
----

By isolating the data into standalone files or pipes, there is no ambiguity parsing raw strings vs files on the command line.

=== Execution Modes

The CLI supports two execution modes via the `--allow-elixir-expressions` flag:

*Restricted Mode (default):*
[source,sh]
----
# Restricts templates to structured Stem expressions only
echo '{"name":"Nina"}' | bin/stem template.stem
----

*Unrestricted Mode:*
[source,sh]
----
# Allows arbitrary Elixir expressions — development only
echo '{"a":1,"b":2}' | bin/stem template.stem --allow-elixir-expressions
----

Use restricted mode (the default) for all production templates and when working with untrusted or user-generated templates.
Only use `--allow-elixir-expressions` for local development and experiments on templates you fully control.

== Runtime APIs

Stem provides runtime evaluation APIs for dynamic template compilation:

[source,elixir]
----
# Restricted by default — structured Stem expressions only
Stem.Unsafe.eval_string("Hello {{name}}", assigns: [name: "Nina"])

# Explicit opt-in for arbitrary Elixir — development/trusted sources only
Stem.Unsafe.eval_string("{{a + b}}", assigns: [a: 1, b: 2], allow_elixir_expressions: true)
----

Always use `allow_elixir_expressions: false` (the default) for production templates.
Only pass `allow_elixir_expressions: true` when the template source is entirely controlled by your team and arbitrary code execution is necessary.

== Helper Capability Groups

Stem enforces capability management for helpers to minimize SSTI attack surface.
By default, only a secure minimum of helpers is available.
Complex data operations require explicit opt-in via capability groups.

=== Available Groups

* **Minimum (always available)** — Escaping, defaults, lookup
* **Strings** — Text manipulation (`trim`, `upcase`, `truncate`, `replace`, etc.)
* **Collections** — Data operations (`map`, `filter`, `sort_by`, `group_by`, `compact`, etc.)
* **Predicates** — Boolean tests (`contains`, `empty?`, `present?`)

=== Loading Groups

*At the call site:*
[source,elixir]
----
Stem.Unsafe.eval_string(
  "{{items |> map(author.name) |> take(5)}}",
  assigns: [items: books],
  transformers: Map.merge(Stem.Transformers.Collections.all(), Stem.Transformers.Strings.all())
)
----

*From configuration:*
[source,json]
----
{
  "transformers": "Stem.Transformers.Collections,Stem.Transformers.Strings"
}
----

*From CLI:*
[source,sh]
----
bin/stem data.json template.stem --transformers Stem.Transformers.Collections,Stem.Transformers.Strings
----

=== Why Capability Groups?

* **Secure by default** — Only essential helpers available
* **Explicit boundaries** — Developers declare what power templates need
* **Auditable surface** — Code review sees exactly which operations are enabled
* **Reduced attack surface** — SSTI attackers face limited operations

For complete details, see xref:architecture:index.adoc[Architecture] documentation.

== Assign Contracts

Templates can declare typed assign requirements using the `contract:` option.
Contracts catch missing or wrongly-typed assigns at render time (or at compile time for unknown type annotations).

=== Basic contract

[source,elixir]
----
Stem.function_from_string(:def, :render, "{{title}}: {{body}}",
  [:assigns],
  contract: [required: [:title, :body], optional: [:subtitle]])
----

=== Typed contract

Specify a type alongside each key.
Valid types: `:string`, `:integer`, `:float`, `:number`, `:boolean`, `:atom`, `:list`, `:map`, `:any`.

[source,elixir]
----
deftemplate :article, "{{title}} ({{count}})", [:assigns],
  contract: [
    required: [title: :string, count: :integer],
    optional: [active: :boolean]
  ]
----

=== Shared contract module

Define the interface once and reference it from many templates:

[source,elixir]
----
defmodule MyApp.Contracts.ArticleView do
  def contract do
    [required: [title: :string, body: :string], optional: [author: :string]]
  end
end

deftemplate :article, "{{title}}", [:assigns],
  contract: MyApp.Contracts.ArticleView
----

== CI Security Gate

Run `mix stem.audit` in CI to fail the build if `allow_elixir_expressions: true` is found in any production config file:

[source,sh]
----
mix stem.audit
# scans config/prod.exs and config/runtime.exs by default

mix stem.audit --paths config/prod.exs --paths config/releases.exs
----

Add to `.github/workflows/ci.yml`:

[source,yaml]
----
- run: mix stem.audit
----

== Security Best Practices

* **Always use `allow_elixir_expressions: false` in production.** It is the default for a reason.
* **Never execute user-generated templates.** If you must, ensure they are validated and safe first.
* **Use HTML escaping by default.** `{{ expression }}` is escaped; use `{{{ expression }}}` only for trusted content.
* **Inject all data via `assigns`.** Do not allow templates to read environment variables or access global state.
* **Register custom helpers instead of enabling arbitrary expressions.** Helper functions keep business logic out of templates.
